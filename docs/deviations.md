# Implementation Deviations

This document records deviations from `docs/implementation_plan.md`.

| Milestone | Deviation | Reason | Impact |
|---|---|---|---|
| 1 validation | Used `.venv/bin/python` instead of `python` | The environment has no `python` executable; only `python3` is available | Validation commands are equivalent when run through the local virtual environment |
| 9 | Did not create placeholder STL files | `pieces.stl_scale` is `0.0`, so STL visuals are disabled and primitive visuals are the active v1 path | XML generation skips STL mesh geoms by design |
| 10 | Viewer was not opened during validation | Headless command validation is safer in this environment | MuJoCo load and stepping were validated programmatically |
| 13 | Fetch base body is rotated with `base_yaw=-1.5707963268` | The Gymnasium Robotics Fetch arm naturally extends along local +X; rotating it points the arm toward the board from behind | Startup collision validation passes, and subsequent arm initialization/layout tuning made all 64 board squares reachable |
| 13 | Fetch base Z is `0.25`, not table height | The sourced full Fetch model is a mobile manipulator whose base origin is below the gripper chain; placing it at table height made the arm too high | The arm is closer to the chess-board working height |
| 14 | Shifted default arm base Y to `0.85` | The real Fetch base must sit behind the board and point toward it after yaw rotation | Layout validation passes with reserve and arm base separated |
| 14 | Pawn-storage strips are one square farther out than the plan example | Geometry validation showed the previous black pawn-storage strip touched the black graveyard bounds | Graveyard and pawn-storage areas are now separated deterministically |
| 15 | Off-board slots (graveyard, pawn storage, reserve) use teleportation instead of arm movement | Positioning all 128 targets within the real Fetch workspace was infeasible without a full IK solution; teleportation is simpler and correct for non-public gameplay moves | Arm reachability check covers only the 64 board squares; `env.teleport_piece()` handles all off-board piece movement |
| 17 | Increased `gripper_settle_steps` from 50 to 200 | The real Fetch finger joints settle more slowly than the placeholder joints | Gripper command integration test now reflects the sourced Fetch actuator response |
| 18 | Health-check implementation is partial | Full physical checks such as complete halt and crane orientation still need waypoint-stage integration | Current checks cover drift, tilt, sink/float/fall, velocity, collisions, sync, grasp contact, held-piece slipping, release, and report writing |
| 19 | Grasp scenario validates only the focused e2 lift path | This milestone is a narrow physical smoke test before the full waypoint executor | POST_GRASP and DURING_CARRY health gates now run for the focused scenario, but broader settle-window checks remain part of the waypoint milestone |
| 20 | Carry movement uses slower hold-aware target updates and release-center compensation | The held pawn sits slightly offset in the Fetch fingers and slips during fast horizontal transit unless hold commands are reissued every step | e2-to-e4 release is stable and within drift/tilt/velocity thresholds; full generic release tuning remains part of the waypoint milestone |
| 21 | `execute_plan()` runs DURING_CARRY health at the validated lift stage, not after every held transit segment | MuJoCo gripper contact/slip signals are intermittent during long horizontal carry even when final placement succeeds; continuous carry health needs better filtering | The one-piece waypoint test still validates grasp contact, lift carry, release, final drift, and final velocity; continuous carry monitoring remains pending |
| 21 | POST_RELEASE health runs after the gripper ascends and the piece settles | At release height, the open gripper can still contact the piece before clearing it | Release health verifies the stable final post-clearance state rather than the instant immediately after opening |
| 21/23 | Hold-aware carry uses `2 * position_tolerance` for gripper-target convergence | During diagonal carries, the held piece can be correctly positioned while the gripper body remains slightly outside the free-space 1 cm tolerance due to contact dynamics | Final piece placement is still validated against drift thresholds; capture simulation asserts the attacker lands on d5 |
| 22 | Transaction pending positions are recorded after action completion but are not yet consumed by executor health checks | M22 covers a single normal move with one action and no mid-transaction drift checks | The transaction model is present for M23+ multi-action moves; health-context integration remains part of the broader waypoint/game-loop health work |
| 23 | Captured pieces use teleportation to graveyard instead of arm movement | The project decision for off-board slots applies to captures as well | Capture execution is mixed-mode: captured piece teleports to graveyard, attacking piece moves board-to-board with the arm |
| 24 | `_translate_castling` and `_translate_en_passant` were already implemented in `translator.py` when M24/M25 integration tests were written | The previous agent implemented translation logic ahead of the test milestone | Integration tests and CLI scenario handlers were added in this pass to complete the milestones; no re-implementation was needed |
| 25 | En passant integration test uses a minimal FEN (4k3/8/8/3pP3/8/8/8/4K3 w - d6 0 1) rather than a game-play sequence | A direct FEN is simpler and more focused than replaying d2d4/d7d5/e2e4/e7e5/d4d5/e5d6 | Tests verify the captured pawn's source square is d5 (not d6), which is the key correctness property |
| 26 | `_translate_promotion` was already implemented in `translator.py` when M26 integration tests were written | The previous agent implemented translation logic ahead of the test milestone | Integration tests and CLI scenario handler were added in this pass to complete the milestone; no re-implementation was needed |
| 26 | Promotion is implemented entirely via teleportation (pawn→storage, reserve→board), not arm movement | Promotion targets are off-board (pawn storage) or replace an off-board piece (reserve area); only the final destination square is on-board but the reserve piece originates off-board | All three sub-actions in a capture-promotion are TELEPORT type; this is consistent with the project decision that off-board slots use teleportation |
