# MuJoCo Robotic Chess Project — Final Instruction Document

## 1. Purpose of This Document

This document is intended to be given to an AI coding agent.

The agent's first task is **not** to immediately implement the project. Its first task is to convert this document into a practical, step-by-step implementation game plan. After the game plan is approved, the agent may implement the project incrementally.

The project is a Python application that simulates a full chess game inside MuJoCo. A human user plays against a computer-controlled opponent, and a Fetch-style robotic arm physically moves the chess pieces on a simulated board.

The implementation should prioritize:

1. Correct chess logic.
2. Reliable MuJoCo simulation behavior.
3. Safe robotic arm movement.
4. Clean architecture.
5. Testability.
6. Debuggability.
7. Config-driven design.
8. Clear documentation.

The goal is not to create a fragile one-move demo. The goal is to create a maintainable side project that can be debugged, tested, and improved over time.

## 3. Project Overview

Build a Python project where:

- The official chess state is managed by `python-chess`.
- A Python UI lets the user select moves.
- A computer-controlled opponent selects legal moves.
- Each legal chess move is translated into one or more physical robotic actions.
- MuJoCo displays the chess board, chess pieces, graveyard, promotion area, and robotic arm.
- A Fetch-style robotic arm moves pieces using a scripted waypoint algorithm.
- Runtime health checks verify that the simulation remains physically valid.
- Logs, tests, and debugging tools make failures easy to diagnose.

The robotic arm should **not** understand chess.  
The chess engine should **not** understand MuJoCo.  
A dedicated translation layer should connect logical chess moves to physical actions.

## 5. High-Level Architecture

The project should use a layered object-oriented architecture.

### 5.1 Chess Logic Layer

Responsible for:

- Holding the official board state.
- Validating moves.
- Applying legal moves.
- Detecting game-over conditions.
- Generating legal moves for AI selection.

This layer should wrap `python-chess` so that the rest of the codebase does not depend directly on it.

### 5.2 Move Selection Layer

Responsible for choosing computer moves.

Initial implementations may include:

- Random legal move selector.
- Basic heuristic selector.

The design should allow a future Stockfish-based selector without rewriting the game loop.

### 5.3 Board Mapping Layer

Responsible for converting between:

- Chess squares such as `e2`, `a1`, and `h8`.
- MuJoCo world coordinates.
- Graveyard slots.
- Promotion reserve slots.

This layer owns board geometry calculations and should be fully config-driven.

The project must define one canonical board orientation, preferably White’s perspective, and use it consistently in the UI, MuJoCo scene, coordinate mapper, move translation code, debug tools, and documentation.

### 5.4 Move Translation Layer

Responsible for translating a legal chess move into physical actions.

Examples:

- Normal move: one physical action.
- Capture: move captured piece to graveyard, then move attacking piece.
- Castling: move king and rook.
- En passant: move captured pawn from its actual square, then move capturing pawn.
- Promotion: remove/promote pawn and place promoted piece.

### 5.5 Physical Piece Registry Layer

Responsible for tracking which logical piece or square corresponds to each concrete MuJoCo body ID. Chess logic treats same-type pieces as mostly interchangeable, but MuJoCo requires stable object identities.

The registry must track:

- Active board pieces and their expected squares.
- Captured pieces and their graveyard slots.
- Promotion reserve pieces and their availability.
- Promoted pieces after they enter play.

The registry must be updated after normal moves, captures, castling, en passant, and promotion. It is required for motion execution, health checks, debugging, and logical/physical synchronization.

### 5.6 MuJoCo Environment Layer

Responsible for:

- Generating XML from config.
- Loading the MuJoCo model.
- Stepping the simulation.
- Querying body positions, contacts, velocities, and orientations.
- Rendering or connecting to the MuJoCo viewer.

### 5.7 Robotic Motion Layer

Responsible for:

- Moving the end-effector using scripted waypoint stages.
- Opening and closing the gripper.
- Executing crane-mode motion.
- Verifying each motion stage.

This layer receives physical movement commands. It should not know chess rules.

The motion controller should operate primarily at the gripper/end-effector target level, similar to the Fetch Pick and Place control style. The waypoint algorithm should generate desired gripper positions and gripper open/close commands. Avoid manually scripting individual joint angles unless required for debugging, safety constraints, or a clearly documented MuJoCo limitation.

### 5.8 Health-Check Layer

Responsible for runtime validations such as:

- Pieces remain upright.
- Pieces do not drift.
- No unexpected collisions occur.
- The target piece is grasped.
- The held piece does not slip.
- The logical board and physical board remain synchronized.

### 5.9 UI Layer

Responsible for:

- Showing the board state.
- Letting the user select a move.
- Showing errors and game status.
- Providing an “AI plays for me” button.

The UI should reflect the official logical board state, not infer chess state from MuJoCo physics.

## 7. Chess Logic Requirements

Use `python-chess` as the authoritative logical chess model.

The chess logic layer must support:

- Legal move validation.
- Illegal move rejection.
- Turn management.
- Check, checkmate, stalemate, and draw conditions available through `python-chess`.
- Castling.
- En passant.
- Pawn promotion.
- Captures.
- Board serialization or debugging output.
- Move history.

The rest of the system should not manually implement chess rules.

Recommended responsibilities for the chess wrapper:

```text
ChessEngine
- get_board_state()
- get_legal_moves()
- is_move_legal(move)
- apply_move(move)
- is_game_over()
- get_game_result()
- get_side_to_move()
```

Computer move selection should be implemented through a separate strategy object:

```text
MoveSelector
- choose_move(board) -> chess.Move
```

Initial move selection can be random or simple heuristic. The architecture should allow replacing it later.

## 8. User Interface Requirements

The UI must be implemented in Python.

The agent may choose a suitable Python UI framework, such as PyQt, Dear PyGui, Pygame, or Tkinter. The chosen framework should work well with the MuJoCo simulation loop and should be simple enough to maintain.

The UI must provide:

- A visual chess board.
- Clear light and dark square coloring.
- Current side to move.
- Selected source square.
- Selected destination square.
- Illegal move feedback.
- Game status.
- Check/checkmate/stalemate feedback.
- A button allowing the AI to play the user’s current move.
- Optional move history.
- Optional reset button.
- Optional debug panel.

User move flow:

1. User selects a piece.
2. User selects a destination square.
3. If promotion is required, the UI asks which piece to promote to.
4. The move is validated by the chess logic layer.
5. If invalid, the UI shows an error and no physical move happens.
6. If valid, the physical move is executed.
7. The logical board is updated only after the physical execution succeeds.

For moves that translate into multiple physical actions, such as captures, castling, en passant, and promotion, the official `python-chess` board should be committed only after the entire physical sequence succeeds. Intermediate physical states may be tracked internally, but the logical chess move should be treated atomically.

The UI board should use the logical board state as the source of truth.

## 9. Chess Move Translation Requirements

The move translation layer converts a legal chess move into physical actions for the robotic arm.

The output should be a list of physical actions, because a single chess move may require multiple arm movements.

The move translator must use the physical piece registry to identify the concrete MuJoCo body IDs involved in each action. It should not rely only on piece type, because multiple pieces of the same type can exist.

The official logical board should not be updated after each physical sub-action. It should be updated only after all physical actions for the chess move complete successfully.

### 9.1 Normal Move

Example:

```text
e2 -> e4
```

Physical action:

1. Move the piece from `e2` to `e4`.

### 9.2 Capture

Physical actions:

1. Move the captured piece from the destination square to the graveyard.
2. Move the attacking piece from the source square to the destination square.

The captured piece should be removed first so that the destination square is clear.

### 9.3 Castling

Physical actions:

1. Move the king.
2. Move the rook.

The implementation should choose and document the safest order. In most cases, moving the king first is logically natural, but the physical order may be chosen based on collision safety.

### 9.4 En Passant

Physical actions:

1. Move the captured pawn from its actual square to the graveyard.
2. Move the capturing pawn to its destination square.

The captured pawn is not on the destination square, so this case must be handled explicitly.

### 9.5 Promotion

The project should support physical promotion.

Recommended strategy:

1. Maintain a promotion reserve area with spare queens, rooks, bishops, and knights for both colors.
2. When a pawn promotes, move the pawn to a captured/promotion storage area.
3. Move the selected promoted piece from the reserve area to the promotion destination square.

This avoids changing the identity and visual model of a piece already in place. The final strategy should be documented.

The promotion reserve should either support multiple promoted pieces of the same type, especially queens, or clearly document a first-version limitation. The physical piece registry must track which reserve piece became active after promotion.

## 10. MuJoCo Environment Requirements

The environment should be inspired by the Fetch Pick and Place environment (https://robotics.farama.org/envs/fetch/pick_and_place/), but adapted for chess.

### 10.1 XML Generation

The MuJoCo XML must be generated by a Python script at application startup.

Requirements:

- Read all important values from config files.
- Write the generated XML to `generated/chess_env.xml`.
- Invoke XML generation from the application entry point, such as `main.py`, before loading MuJoCo.
- Load the generated XML into MuJoCo.
- Avoid hardcoded geometry or physics values.
- Generate repeated structures programmatically, especially board squares and pieces.

The XML generator should create:

- World/body setup.
- Board.
- 64 chess cells.
- Chess pieces.
- Graveyard slots.
- Promotion reserve slots.
- Materials and colors.
- Fetch-style robotic arm.
- Optional debug markers when debug mode is enabled.

### 10.2 Board Geometry

Each chess cell must be:

```text
0.07 m x 0.07 m
```

The board is therefore at least:

```text
0.56 m x 0.56 m
```

The board should have a configurable thickness and position.

Square centers should be calculated from:

- Board origin.
- Square size.
- File index.
- Rank index.

Do not manually specify all 64 square positions.

### 10.3 Board Coloring

The board must visually resemble a standard chess board:

- 64 visible cells.
- Alternating light and dark colors.
- Consistent mapping between visual board orientation and chess notation.

The mapping from `a1` through `h8` to MuJoCo coordinates must be documented. The UI, MuJoCo scene, debug tools, and board mapper must all use the same orientation convention.

### 10.4 Chess Piece Physical Shape

The physical collision shape should be optimized for reliable robotic manipulation, not visual realism.

Recommended approach:

- Use simple primitive collision geometry.
- Use a stable cylindrical or capsule-like graspable body.
- Keep a low center of mass.
- Use a base wide enough to reduce tipping.
- Use a consistent grasp region across piece types.

All pieces may share similar physical collision dimensions to simplify grasping.

### 10.5 STL Visuals

Each piece should have an STL visual decoration corresponding to its chess type.

However:

- STL meshes should be visual-only.
- STL meshes should not drive collision behavior.
- Collision should come from simple primitive geoms.
- Visual realism should not compromise physics stability.

### 10.6 Piece Placement

Pieces must spawn:

- Centered on the correct squares.
- Upright.
- Resting on top of the board.
- Not sinking into the board.
- Not floating noticeably above the board.
- With stable initial velocities.

Piece spawn heights must be calculated using board height, board thickness, and piece collision geometry.

After the environment loads and all pieces spawn, run an initial settle phase before gameplay begins. After settling, run health checks to verify that no piece drifted, tilted, sank into the board, fell, or retained problematic velocity.

### 10.7 Graveyard

The graveyard stores captured pieces.

Requirements:

- Reachable by the arm.
- Does not interfere with active gameplay.
- May be beside the board, on a separate platform, or on the floor.
- Recommended first-version approach: a slot-based area beside the active board.
- Collision-safe.
- Large enough for all captured pieces.
- Slot-based and config-driven.
- Preferably separated by piece color.
- Allocates slots deterministically, for example by color and capture order.

The graveyard allocation must be tracked in the physical piece registry so health checks know where each captured piece is expected to be.

### 10.8 Promotion Reserve

If using reserve pieces for promotion, add a promotion reserve area.

Requirements:

- Reachable by the arm.
- Outside the active board.
- Not interfering with the graveyard.
- Contains spare queen, rook, bishop, and knight pieces for each color.

### 10.9 Remove Fetch Target Dot

The final environment must not include the red Fetch target dot or goal marker.

Explicitly remove or avoid generating:

- Red target site.
- Goal marker geom.
- Unused Fetch goal visualization.

## 11. Robotic Arm Requirements

Use the Fetch-style robotic arm from the Fetch Pick and Place environment as the basis for the robot.

The arm must be adapted to the larger chess board.

### 11.1 Crane Mode

The arm should operate in “crane mode.”

Crane mode means:

- The gripper approaches pieces from above.
- Low-altitude horizontal movement over the board is avoided.
- Pickup and placement are mostly vertical.
- Horizontal transit happens at a safe height above all pieces.
- The arm returns to a safe home position after each action.

Crane mode should be enforced through the waypoint algorithm and, where useful, through environment design and safety checks.

### 11.2 Reachability

The arm must be able to reach:

- Every chess square.
- Every graveyard slot.
- Every promotion reserve slot.
- The home position.
- Hover positions above all of these.

The agent must not assume reachability. It must implement a reachability validation/debug tool.

If the default Fetch arm placement is insufficient, adjust:

- Board position.
- Arm base position.
- Arm mount height.
- Home position.
- Safe hover height.

The arm base must not intersect the board in a way that causes physical instability or unintended collisions.

### 11.3 Collision Avoidance

The motion system should avoid collisions by design and detect unexpected collisions through health checks.

Important collision categories:

- Arm with board.
- Gripper with board.
- Arm/gripper with non-target pieces.
- Held piece with other pieces.
- Held piece with board.
- Piece with piece.
- Arm with graveyard or promotion area.
- Unexpected self-collision if detectable.

## 12. Waypoint Algorithm Requirements

The project must not use reinforcement learning for arm movement.

Instead, implement a scripted waypoint algorithm that outputs gripper/end-effector target positions and gripper commands. MuJoCo should handle the robot dynamics/control behavior as much as practical, following the Fetch-style end-effector control concept. Manual joint-level scripting should be avoided unless specifically justified and documented.

The algorithm receives commands such as:

```text
Move physical piece P from source position A to destination position B.
```

The arm controller does not know chess. It only knows physical positions and piece IDs.

### 12.1 Standard Action Flow

Each physical move should follow this high-level flow:

1. Start at or move to `HOME_POSITION`.
2. Move to a safe hover point above the source.
3. Descend vertically to the grasp height.
4. Close the gripper.
5. Ascend vertically to safe hover height while carrying the piece.
6. Move horizontally to a safe hover point above the destination.
7. Descend vertically to the release height.
8. Open the gripper.
9. Ascend vertically.
10. Return to `HOME_POSITION`.

This list describes only the **active motion/control stages**. Health checks and passive settle windows must not be modeled as waypoint stages. They should be handled by the motion executor and the health-check system around each waypoint stage.

### 12.2 Waypoint Stages

Represent active motion/control steps as explicit stages, not as one large function.

Suggested active stages:

```text
MOVE_TO_HOME
MOVE_TO_SOURCE_HOVER
DESCEND_TO_GRASP
CLOSE_GRIPPER
ASCEND_WITH_PIECE
MOVE_TO_DESTINATION_HOVER
DESCEND_TO_RELEASE
OPEN_GRIPPER
ASCEND_AFTER_RELEASE
RETURN_HOME
```

Each active stage should:

- Have a clear target or gripper command.
- Log start and end.
- Have a timeout.
- Fail clearly if it cannot complete.

### 12.3 Hold-Aware Settle Windows Around Every Stage

The motion executor must insert a settle window **before and after every active waypoint stage**. These settle windows are not waypoint stages. They are executor-managed stability windows used to verify that the system can maintain the required state for more than one simulation step.

During a settle window:

- The arm must not start a new movement stage.
- The gripper/end-effector target should remain unchanged.
- The simulator should step for a configurable number of steps.
- Relevant health checks should run from the Health Checks system.
- The system should verify that the required state remains stable across the entire settle window.

Important: “no new action” must not mean “release all control.” The executor must continue applying whatever control is required to maintain the current state. For example, if the gripper is holding a chess piece, the gripper must continue applying the configured holding command/tension/closed-width control during the settle window. Otherwise, the piece may slide or fall even though the arm is not intentionally moving.

In other words:

- If the arm is hovering empty-handed, maintain the current end-effector target and gripper state.
- If the arm is holding a piece, maintain the current end-effector target and maintain gripper holding tension.
- If the gripper has just released a piece, keep the gripper open and maintain the current end-effector target while verifying that the piece remains stable.
- Do not move to the next stage until the required state is stable and all relevant health checks pass.

This is important because some physics bugs do not appear immediately. A piece may initially look stable, then drift, tilt, slip, or collide a few simulation steps later. The settle windows are intended to catch these bugs early and localize them to the stage that caused the problem.

Examples:

- Before `DESCEND_TO_GRASP`, settle and verify that all non-target pieces are still stable.
- After `CLOSE_GRIPPER`, settle while maintaining gripper holding tension and run grasp verification checks.
- After `ASCEND_WITH_PIECE`, settle while maintaining gripper holding tension and verify that the held piece is not slipping.
- After `OPEN_GRIPPER`, settle with the gripper open and run release verification checks.
- After `RETURN_HOME`, settle and verify the full physical state before the chess move is committed logically.

### 12.4 Complete-Halt Requirement Between Stages

After every active waypoint stage, the arm must reach a complete stopping state before the executor may continue to the next active stage. This requirement is separate from merely reaching the target position.

A stage is complete only when all required conditions are true:

- The gripper/end-effector reached the target position within tolerance.
- The arm and gripper velocities are below configured linear and angular velocity thresholds.
- If a piece is being held, the held piece velocity is also below configured thresholds relative to the gripper and world.
- If the stage involved release, the released piece is stable on the board/graveyard surface and below configured velocity thresholds.
- The relevant post-stage settle window completed successfully.
- All relevant health checks passed.

This is required so that leftover velocity from one stage does not affect the next stage. For example, a fast descent must not be followed immediately by gripper closing while the arm is still moving, and a horizontal transit must not be followed immediately by descent while the held piece is still swinging or sliding inside the gripper.

The velocity thresholds, settle duration, and timeout values must be configurable. If the system cannot reach a complete halt before timeout, the stage must fail clearly and produce diagnostics.

### 12.5 Safe Hover Height

Safe hover height must be calculated from config and geometry.

It must clear:

- Board top.
- Tallest active piece.
- Gripper geometry.
- Held piece geometry.
- Graveyard pieces.
- Safety margin.

Do not hardcode it blindly.

### 12.6 Grasp Height

Grasp height must account for:

- Board top Z.
- Piece geometry.
- Desired grasp region.
- Gripper finger geometry.
- Contact margin.

The grasp point should be high enough to avoid board collision and low enough to avoid unstable tipping.

### 12.7 Release Height

Release height must allow gentle placement.

The piece should not be dropped from a high distance.

The release sequence should:

1. Bring the piece very close to the destination surface.
2. Open the gripper gradually if needed.
3. Let the motion executor run the passive post-stage settle window.
4. Let the Health Checks system verify that the piece is upright, centered, stable, and released.
5. Continue to the next active motion stage only if those checks pass.

### 12.8 Gripper Control

The gripper controller should support:

- Open.
- Close.
- Hold.
- Configurable open width.
- Configurable grasp width.
- Gradual opening and closing.
- State reporting needed by health checks to determine whether the target piece is held.

The gripper should not open unnecessarily wide, because that may collide with neighboring pieces.

### 12.9 Smooth Motion

The arm should move gradually over multiple simulation steps.

Do not teleport pieces or the gripper during normal execution. The implementation must not hide physics failures by silently snapping pieces into the correct location after a failed movement. Teleportation or state correction is allowed only in explicit reset/debug utilities, never as part of normal successful gameplay.

The motion executor should track:

- Target position.
- Actual gripper position.
- Position tolerance.
- Step count.
- Timeout.
- Contact state.
- Stage result.

## 13. Health Checks

Health checks are runtime validations designed to detect problems early and make debugging easier.

They should run at important points, such as:

- Application startup.
- After environment load.
- After initial settle.
- Start of turn.
- During the hold-aware settle window before each active waypoint stage.
- During the hold-aware settle window after each active waypoint stage.
- After the gripper closes, to verify grasp.
- While carrying a piece, to verify that it is not slipping.
- After the gripper opens, to verify release.
- End of turn.

Health checks are not waypoint stages. The waypoint system defines active motion/control stages, while the health-check system validates the state around those stages, especially during settle windows. During those windows, the arm should not begin a new movement, but the controller must still maintain the current end-effector target and any required gripper holding tension.

### 13.1 Required Checks

Implement checks for at least:

- Piece tilted or fallen.
- Piece drifted from expected square or slot.
- Piece sunk into board.
- Piece floating unexpectedly.
- Piece fallen to floor.
- Piece unexpectedly moving during settle.
- Arm, gripper, held piece, or released piece failing to reach complete halt before the next stage.
- Target piece not grasped after gripper closes.
- Held piece slipping from gripper.
- Held piece moving too much inside gripper.
- Gripper not maintaining required holding tension during settle while carrying a piece.
- Piece not released correctly.
- Unexpected arm-board collision.
- Unexpected gripper-board collision.
- Unexpected arm-piece collision.
- Unexpected piece-piece collision.
- Logical chess board not synchronized with physical piece registry.

### 13.2 Failure Behavior

When a health check fails:

1. Halt the current move.
2. Prevent the logical chess state from being updated if the physical action did not complete.
3. Write detailed logs.
4. Save a diagnostic failure report.
5. Notify the user through the UI or console.
6. Preserve enough information for debugging.

A failure report should include:

- Chess move.
- Physical action.
- Waypoint stage.
- Piece IDs.
- Expected and actual positions.
- Orientations.
- Velocities.
- Contacts.
- Relevant config values.
- Health-check result details.

## 21. Open Design Decisions the Agent Must Address

The choice should consider:

- Simplicity.
- Maintainability.

- Ease of drawing a chess board.

### 21.2 Physical Piece Shape

Decide the exact primitive collision geometry.

The priority is:

1. Easy grasping.
2. Stable placement.
3. Low tipping risk.
4. Simple collision behavior.
5. Visual chess identity through STL decoration.

### 21.3 Promotion Strategy

Decide and document how promotion is physically represented.

Recommended: reserve pieces plus pawn removal.

### 21.4 Graveyard Layout

Decide and document graveyard placement and slot allocation.

It must be reachable and collision-safe.

### 21.5 Arm and Board Placement

Determine whether the default Fetch arm placement is sufficient.

If not, adjust environment geometry and validate with reachability tests.

### 21.6 Grasp Strategy

Decide the standard grasp region and gripper widths.

All piece types should preferably share a consistent graspable region.

## 22. Final Guidance to the AI Agent

When uncertain, prefer:

- Simpler geometry.
- More stable physics.
- More explicit stages.
- More logging.
- More health checks.
- More tests.
- More documentation.

Do not hide physics problems by silently teleporting pieces or ignoring failed checks.

Do not update the official chess board if the physical move failed.

Do not let UI code, chess logic, motion control, and MuJoCo simulation become tangled together.

The key architectural boundary is:

```text
Chess move -> physical action list -> waypoint execution -> health checks -> logical board update
```

Build the system so that every step can be tested and debugged independently.
